## 1. Recommendation (bottom line first)

1. **Build all three dashboards as read-only views over `db_TCL`, through one ported guard layer (new scoped login, statement guard, zero Prisma introspection of the ERP)** — ship **Sales first** on `tbl_DOhdr` (the only table with real, arithmetically-reconciled volume today), **Purchase** on `PurchaseInvoiceHdr` with `PurchaseOrderHdr` as a permanent secondary card, and **Production** honestly as plan-only. Every basis is a swappable value, never a hardcoded assumption.
2. **Never extend the existing full-sysadmin `orderstock_app` ("sa") connection to these reads** past a time-boxed, guard-wrapped, fixtures-only dev interim. A new scoped `db_datareader`-only login (`orderstock_dash`) is a **hard go-live gate** for Phase 2 onward, not a nice-to-have. This caution is not speculative: the sibling TCL project's own `README.md` status table (read directly this session) shows its own `db_datareader`-restricted login was still "⏳ รอฝ่าย ERP จัดเตรียม login" (pending) as of TCL's last-read commit — even though exploratory querying there had already happened via other credentials. Plan for the same lead time here, even though the ERP team is internal.
3. **Every total ships with its basis labeled, and Sales ships with an explicit reconciliation footnote**: the shown DO-based ฿234,403 is real and internally consistent, but a larger, currently-**excluded** pool of ฿858,937.21 (3 `SalesInvoiceHdr` rows, `DocuType='SI'`) exists in the same ERP and must never be silently omitted from the customer's view.
4. **Fix the deploy and doc debt in Phase 0, before any dashboard code assumes a baseline that isn't live.** Two corrections from this pass: the production host is **verified 15 commits** behind local `main` (`git log --oneline fe2df61..HEAD` = 15, not the previously-cited "~12"), and `db/alter-shop-add-location.sql` still has not run against `db_TCL`. Separately, `process/context/database/all-database.md:411` and `process/context/tests/all-tests.md:161` both wrongly claim the sandbox is an "ERP-shaped clone" with a `krs_log` table — verified false (10 tables total: orderstock's 9 + `_prisma_migrations`). This is not a one-line deletion: **both files use that wrong premise to justify a downstream recommendation** ("avoid `prisma migrate dev`, use hand-authored ALTER + `prisma generate` instead") that may itself now be over-cautious for a sandbox proven to hold no foreign tables — Phase 0 must read both files in full and re-examine anything chained off the same premise, not just delete the one sentence.
5. **Build a small ERP-shaped fixture sandbox and a manual reconcile script against KRS's own report procedures before any dashboard is called done.** There is zero automated ERP test path today, and reconciling against `sp_PurchaseInvoiceMonth` / `sp_Popending` / DO's own header=detail identity is the cheapest way to earn trust in numbers pulled from a shared live accounting database.

## 3. Architecture

**ERP read layer — `src/lib/erp/`** (ported from the sibling TCL project's `erp-adapter.ts` — **confirmed to exist on disk this session** at `/Users/innovera/Documents/TCL/server/src/erp/` — `erp-adapter.ts` (33.6KB) + a `drivers/` subdirectory + `erp-secret.ts` + `erp.module.ts`, matching the described 5-layer guard exactly, framework-agnostic, adapted for orderstock):
- `pool.ts` — a **second, independent `mssql.ConnectionPool`**, small (max 2-3), its own query timeout. Raw `mssql` (already a pinned dependency, `mssql@^12.2.0`), never `prisma.$queryRaw`. **Lifecycle requirement (confirmed via direct read of `src/lib/db.ts`)**: this pool MUST use the exact same dev-hot-reload singleton guard `db.ts` already uses — a `globalForX`-style cache (`globalForPrisma.prisma ?? new PrismaClient(...)`, refreshed under `NODE_ENV !== "production"`) — never a per-request pool. `db.ts`'s own comment states the connection "binds per instance," which is exactly why a naive port without the same guard would leak pools under Next dev-mode hot reload the same way the existing code warns against for Prisma.
- `guard.ts` — single choke point `guardedQuery()`. Tokenizes SQL, requires `SELECT`/`WITH` only, rejects multi-statement text, denylists 19 write/DDL keywords (INSERT/UPDATE/DELETE/MERGE/TRUNCATE/DROP/ALTER/CREATE/GRANT/REVOKE/EXEC(UTE)/sp_executesql/xp_cmdshell/BULK/OPENROWSET/INTO/BACKUP/RESTORE/SHUTDOWN). Ported with its ~24-case unit-test suite (`test/erp-read-only.spec.ts` in the source project).
- Two more layers worth porting, confirmed present in the source adapter and cheap to carry over: an **interface-level compile-time type-guard** (no method on the adapter interface may match a write-ish name prefix — `push/insert/update/delete/save/...` — making an accidental write method a compile error, not just a runtime guard) and a **connection-level `ApplicationIntent=ReadOnly` option** (effective only behind an Always-On listener, but free to set).
- Boot probe — `IS_SRVROLEMEMBER`/`HAS_PERMS_BY_NAME` check; refuses to start the ERP module on a write-capable login.
- `mock-driver.ts` — offline driver for local dev/Playwright, mirroring TCL's own mock pattern.
- **Login**: new scoped `db_datareader`-only login, e.g. `orderstock_dash`, distinct from `orderstock_app` ("sa"). **Interim, time-boxed exception**: until the login lands, Phase 1 may run the guard against the existing 'sa' connection **only** for local dev/CI against the fixture schema — never wired into anything a real user reaches. Phase 2+ go-live is hard-gated on the scoped login existing.
- **Never add ERP tables to `prisma/schema.prisma`** (no `tables.external` entries). `prisma db pull` always introspects the *entire* connected database regardless of an `external` allowlist — on `db_TCL` ("hundreds of unrelated tables," 258 confirmed via direct table listing) that is a heavy, undocumented-risk operation for a Preview-status feature with no drift check.
- **SQL lives in versioned files**, not inline TypeScript: `db/erp-queries/{purchase,sales,production}/*.sql`, loaded and run verbatim — diffable, revocable without a redeploy, and reviewable by KRS's own ERP team (who already own `sp_PurchaseInvoiceMonth`, `sp_Popending`, etc.).

**Caching / isolation / degradation:**
- `db_TCL` has `READ_COMMITTED_SNAPSHOT` **off** (stated as a given fact; not independently re-verified this session or the prior ERP research session — treat as accepted-as-given) — use `WITH (NOLOCK)` on the read-heavy aggregation SELECTs in `db/erp-queries/`; acceptable dirty-read risk for a dashboard, unacceptable for financial posting (not attempted here).
- There is no deliberate read-side query cache today (`unstable_cache`, tagged `revalidate`, `'use cache'` are all unused; most `(main)/` routes are `force-dynamic` by design). `revalidatePath()` *is* called 30+ times across `actions.ts` files, but only as the App Router's write-path cache invalidation after a mutation — it is not a query-result cache dashboards can reuse. Add a purpose-built short-TTL (~5 min) `unstable_cache` wrapper specifically around ERP dashboard reads.
- New `/api/health/erp` route, decoupled from the existing `/api/health`, mirroring TCL's own `/healthz` vs `/healthz/erp` split — ERP downtime must never flag orderstock itself as unhealthy. On timeout/error: serve the last cached value + a visible "ข้อมูลอาจไม่ล่าสุด" banner, never a 500.

**UI shell:**
- New `nav-links.tsx` group "แดชบอร์ด" → `(main)/dashboards/{purchase,sales,production}/page.tsx`, each `force-dynamic` + `requireAuth()`, mirroring `/history`'s convention.
- **Do not add a 4th tab to `bottom-tab-bar.tsx` in v1** — it hardcodes exactly 3 tabs and an existing Playwright assertion (`e2e/mobile.spec.ts`) checks that. Dashboards are sidebar/drawer-reachable only (tablet/desktop) until real usage justifies deliberately revisiting that gate.
- **Charts**: default to the proven hand-rolled CSS/div bar pattern already in `/summary` (zero new dependency, guaranteed Thai-font/dark-mode fidelity — confirmed via `package.json`: no chart library of any kind is installed today). **Introducing Recharts is a new-dependency decision, not an "adopt vs. fallback between two known options" choice** — neither `recharts` nor `react-is` appears anywhere in `package.json`, so no peer-dependency behavior against this repo's pinned React 19.2 has actually been observed. Treat React-19 peer-dep compatibility as **UNTESTED/UNKNOWN**, not as a specific known failure mode. Run **one** spike embedded in the **Sales** dashboard's first chart (the best-data dashboard, built first): `pnpm add recharts` (and `react-is` only if the installer's own peer-dep warnings ask for it), record whatever peer state actually resolves, then build one Thai-labeled chart (light+dark). Pass → adopt for Purchase/Production too. Fail, or peer resolution is unacceptable → CSS-bar fallback everywhere, no second spike needed.
- Reuse `src/components/ui/card.tsx` for KPI tiles and `chip.tsx` (6 tones) for PO/MO/DO status pills — no new primitives required for either.
- Pilot-window banner on every dashboard ("ข้อมูลนำร่อง 14 ส.ค.–ปัจจุบัน") — pilot volumes (4 POs, 73 DOs, 3 MOs, ~5-week window) will otherwise read as broken.

**Filters + drill-down URL model:**
- URL `searchParams` throughout (`?from=&to=&supplier=&status=`), extending the one existing precedent — `shop-location-filter.tsx`'s `useRouter`-navigate-on-change pattern — to multiple params. A new date-range component is required; none exists today (only a single native `<input type=date>` + `be-date.ts` BE display).
- Drill-down is a real navigation to a filtered/detail route (e.g. `/dashboards/purchase?supplier=ช-001` → PO list → PO detail), matching the app's existing zero-client-modal-state philosophy — the only precedent, `/history` row → `/orders/[id]`, is a full navigation too.

**Access control:**
- `requireAuth()` opens all 3 routes to ADMIN+STAFF (matches `/shops`/`/products`). Every ฿-denominated card/query is **individually gated server-side** by an explicit `canSeeMoney` check (never client-side hiding). **Confirmed via direct read of `src/lib/auth-guard.ts`**: `requireAuth(requiredRole?: Role): Promise<AuthedUser>` checks at most one exact required role and returns `{ id, username, role }` — it has no field-level or multi-role concept today. `canSeeMoney` is therefore **new inline logic against the returned `AuthedUser.role`** (e.g. `const { role } = await requireAuth(); const canSeeMoney = role === "ADMIN";`), not an extension of `requireAuth()`'s own signature. There is no existing "view money, can't edit" precedent in this codebase, so the default (ADMIN-only) needs explicit customer confirmation (Decision 3 below).

## 5. Testing & verification strategy

1. **Pure-function unit tests** (DB-free) for every basis resolver, status `CASE`, and aggregation helper — mirrors the existing `totals.ts`/`summary.ts`/`roster.ts`/`locations.ts` convention exactly. New `src/lib/dashboards/__tests__/`.
2. **ERP-shaped fixture tables** in the sandbox, separate schema, plain hand-written SQL (not Prisma-managed — the sandbox has confirmed zero ERP tables today, contradicting the stale docs fixed in Phase 0). Seed synthetic rows reproducing the exact documented edge cases: `IsClosed` NULL-when-open on `PurchaseOrderHdr`, `DocuType='SI'` vs `'SA'/'SE'/'SC'` on `SalesInvoiceHdr`, `tbl_Dodtl.SoNo` NULL-on-all-rows, the `SONo` column-name collision (a different, DO-numbered column on `InventoryFlowDtl`), `Prodqty≡LotQty` copy-of-plan.
3. **Ported guard unit tests** — the ~24-case `assertReadOnlySql`/`guardedQuery` suite from TCL, adapted.
4. **Mock ERP driver for Playwright** — dashboard e2e specs need no live DB connection, mirroring `auth.setup.ts`'s fixture precedent and TCL's own mock-driver approach.
5. **Manual (never CI — none exists) live reconcile script**, run against `db_TCL` before each dashboard's go-live gate and periodically after: diff dashboard totals against KRS's own report procedures (`sp_PurchaseInvoiceMonth` logic, `sp_Popending`, and DO's own header=detail identity).
6. **Playwright role/redirect gates** for the 3 new routes, mirroring `e2e/auth.spec.ts`.

## 6. Decisions for the user (ranked by plan impact)

1. **Sales basis** — Options: (a) ship DO now as provisional, AppSetting-toggle to SO/Invoice later; (b) wait for real SO/Invoice adoption before shipping anything. **Recommended: (a)** — DO is the only reconciled real volume today; the toggle costs nothing extra and avoids blocking the whole program on a business-process change outside this team's control.
2. **Purchase framing** — Options: (a) show both Invoice (461,140) and PO (727,920) as permanent dual cards; (b) pick one. **Recommended: (a)** — both are correct-by-construction answers to different questions (billed vs committed); picking one hides real information for no benefit.
3. **Who sees ฿ figures** — Options: ADMIN-only vs ADMIN+STAFF. **Recommended: ADMIN-only** as the default, pending explicit confirmation — no existing "view-money-can't-edit" precedent exists in this codebase (confirmed: `requireAuth()` has no field-level concept, see §3), and money visibility should be a deliberate choice, not an accident of a coarse-grained default.
4. **ERP login policy** — Options: (a) hard-gate all shipping work on the scoped login; (b) allow a permanent 'sa'-fallback interim. **Recommended: (a), with a *time-boxed* dev-only interim** — never ship past Phase 1 on 'sa', but don't block Phase 1's guard/fixture work on an external approval either. The sibling TCL project's own `README.md` (confirmed read directly this session) shows its equivalent login request was still pending at last read — plan the timeline conservatively even though the ERP team is internal.
5. **Chart library** — Options: (a) hand-rolled CSS bars only; (b) treat Recharts adoption as a new-dependency decision, gated by a spike. **Recommended: (b)**, spike embedded in Phase 2 (Sales) — nothing about recharts/react-is peer compatibility with this repo's React 19.2 is known today (neither package is installed); the spike's job is to find out, not to confirm an assumed outcome, on the dashboard with the most real data to render, before committing to it everywhere.
6. **Caching** — Options: (a) no cache, live query every request; (b) short-TTL `unstable_cache` wrapper. **Recommended: (b)**, 5-minute TTL — pilot data changes at most daily; a live query per request adds needless load on a shared production ERP database.
7. **Mobile nav** — Options: (a) add a 4th `bottom-tab-bar.tsx` tab now; (b) sidebar/drawer-only in v1. **Recommended: (b)** — avoids a real, avoidable regression against the existing 3-tab-nav Playwright gate; revisit deliberately once usage data justifies it.
8. **Production scope** — Options: (a) ship plan-only from `LotQty` now, regardless of `tbl_BatchMRP`; (b) wait for the Phase 0 `tbl_BatchMRP` row-data check before finalizing. **Recommended: (b)** — the row COUNT is already known (20, confirmed via `tables.json`), but the actual `ReqQty`/`SchedRecQty`/`PlanRecQty` VALUES are not; that one cheap query is already scheduled in Phase 0 — don't lock a plan-source design a query away from being provably wrong.

## 8. Risks & mitigations (top 8)

1. **`sa`-connection blast radius reused for dashboard reads** → hard gate on the scoped `orderstock_dash` login before Phase 2 ships; 'sa' usable only behind the guard, dev/fixtures-only, time-boxed.
2. **Unscoped `prisma db pull` against hundreds of unrelated ERP tables** → never run it; raw `mssql` queries via versioned `.sql` files only; `schema.prisma` stays untouched.
3. **No FK integrity across the PO/SO/DO/Production document chains, plus a real column-name collision** (`InventoryFlowDtl.SONo` is populated with *DO* numbers, not SO numbers, despite the name matching `SalesOrderHdr`'s own concept) → every join is a defensive LEFT JOIN with a self-check assertion (e.g. DO header total == detail sum); the `SONo` collision is documented inline in the query file that touches it.
4. **Flag-derived status logic is genuinely unproven at scale** — `IsClosed` is `NULL`-when-open (not `0`) on `PurchaseOrderHdr`, and only 2 of 7 CASE branches have ever fired (n=4) → visible "unvalidated" badges, unit tests locked to the exact documented fixture rows, never silently presented as authoritative.
5. **Zero automated ERP test path today** (sandbox holds exactly 10 tables, none ERP-shaped) → fixture schema is a Phase 1 blocker, not deferred; the stale docs claiming otherwise are fully corrected in Phase 0, including the downstream guidance they were used to justify.
6. **Pilot-scale data (4 POs / 73 DOs / 3 MOs, ~5-week window) reads as broken or misleading** → mandatory pilot-window banners on every dashboard; never a fabricated 0%/100% achievement tile.
7. **A larger, excluded `SalesInvoiceHdr` pool (฿858,937.21) sits next to the shown DO figure (฿234,403)** → explicit reconciliation footnote on the Sales dashboard; silently omitting the larger, disputed number is itself a trust risk with a customer who can independently check the ERP.
8. **Chart-library adoption is an unverified new-dependency decision** (neither `recharts` nor `react-is` is installed; React-19 peer-dep behavior is unknown, not just untested-in-this-repo) → one cheap spike inside the Sales dashboard (best data, built first) that installs the package and records the *actual* result, not a blind company-wide adoption on an assumed compatibility story; proven CSS-bar fallback if it fails.

## 9. Rejected alternatives

- **Add ERP tables to `prisma/schema.prisma` via `tables.external`** — rejected: `prisma db pull` always introspects the entire connected database regardless of the allowlist; too heavy for a Preview-status feature with no drift check.
- **Use Prisma `$queryRaw`/`Prisma.sql` for ERP queries** — rejected, but on a re-verified basis: `orm#28963` (`Prisma.sql` composition inside `$queryRaw` serializing as JSON) was looked up directly this session — reported against 7.2.0 as a regression from 6.18.0, and closed 2026-03-14 (`stateReason: COMPLETED`) after a Prisma maintainer could not reproduce it on 7.4.0/7.5.0-dev.6 and asked for a fresh repro that never arrived. It is therefore **likely, but not confirmed, already fixed** by orderstock's pinned 7.8.0. The rejection stands regardless: raw `mssql` (`mssql@^12.2.0`, already a direct dependency) is the simpler, already-precedented escape hatch, and depending on a raw-SQL composition path in a Preview-adjacent feature against a live shared ERP database isn't worth it even if the specific bug is gone.
- **Reuse the existing `sa`/`orderstock_app` connection for ERP reads long-term** — rejected: needlessly extends full-sysadmin blast radius on a live shared accounting database; a scoped pool/login is cheap and already precedented by the sibling TCL project (confirmed to exist and use the same pattern).
- **DBA-created SQL VIEWs as the access layer** — rejected for v1: creating a view is itself DDL against `db_TCL`, the same manual-DBA gate as any other schema change, without materially reducing app-side guard work; revisit only if the `.sql`-file approach proves insufficient.
- **Ship a Production achievement-% tile from `Prodqty`/`PlanQty`** — rejected: proven to be a copy-of-plan artifact (always exactly 100%); would be a fabricated metric, not a measurement.
- **Add a 4th `bottom-tab-bar.tsx` mobile tab for dashboards in v1** — rejected: the hardcoded 3-tab array has a passing e2e assertion; promote to a mobile tab only after usage data justifies deliberately revisiting that gate.
- **Adopt a client chart library uniformly across all three dashboards up front, on the assumption it will work** — rejected: nothing about Thai-font-in-SVG or React-19 peer-dependency behavior is known in this codebase (neither package is installed); gate behind one spike on the best-data dashboard first, and let the spike's actual result — not an assumed one — decide.
- **Treat `SalesOrderHdr`/`SalesInvoiceHdr` as the literal Sales ฿ basis, exactly as the requirement bullet names "SO"** — rejected: SO has 1 unusable row (`SoStatus` NULL); Invoice's only 3 live rows are `DocuType='SI'`, excluded by the ERP's own `sp_SalesAmount`/`sp_SalesInvoiceMonth` filters; either would render a near-zero, misleading dashboard against real ฿234,403 of actual deliveries.
